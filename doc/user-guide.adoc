== Overview

`karate-gradle` is a Gradle-native, workflow-driven test execution plugin built on top of Karate.
It gives you a stable entry point for regression-style runs while keeping execution inside the
JUnit Platform ecosystem so that JUnit-based tooling integrations continue to work.

At a high level, the plugin provides:

* A `regression { }` DSL for workflow, environment, dataset, and reporting configuration
* A `regressionRun` task for workflow-aware execution
* Generated JUnit entry points so Karate scenarios run through JUnit Platform
* Opt-in reporting integrations such as Allure and ReportPortal

The core execution inputs are:

* `workflow`
* `env`
* `dataset`
* `commit`

Those inputs drive reproducible runs across local development and CI.

== Mental Model

=== What `regressionRun` actually does

`regressionRun` does not launch Karate's legacy standalone CLI main class.
Instead, it:

. Loads the selected workflow definition
. Resolves the effective environment configuration
. Resolves the dataset path
. Generates system properties for Karate and reporting integrations
. Forks a JVM with the consumer project's test runtime classpath
. Launches a generated JUnit Platform entry point

That generated entry point consists of:

* `KarateRunner`
  A generated JUnit5 `@TestFactory` class that builds the Karate run from system properties
* `KarateJUnit5Launcher`
  A generated `main` class that executes the JUnit Platform launcher

This architecture is important because many ecosystem integrations for Karate work through JUnit.

=== Execution flows

[source,text]
----
regressionRun  ->  KarateJUnit5Launcher  ->  JUnit Platform  ->  Karate HTML report
                                                     ->  JUnit listeners such as Allure / ReportPortal

test           ->  Gradle Test           ->  JUnit Platform  ->  JUnit listeners such as Allure / ReportPortal

allureReport   ->  build/allure-results  ->  Allure HTML report
----

Use `regressionRun` when you want workflow-aware execution with dataset, environment, and commit inputs.
Use `test` when you want the standard Gradle JUnit entry point.

== Quickstart

=== Apply the plugin

[source,kotlin]
----
plugins {
    id("org.openprojectx.karate.gradle") version "0.1.75"
}
----

The plugin automatically adds `io.karatelabs:karate-junit5` to `testImplementation`.

=== Minimal configuration

[source,kotlin]
----
regression {
    workflowsDirs.add("src/test/resources/workflows")
    environmentsDirs.add("src/test/resources/environments")
    datasetsRootDir.set("src/test/resources/datasets")
    datasetProvider.set("local")

    datasets {
        register("default") {
            path.set("default")
        }
    }
}
----

=== Minimal workflow

[source,hocon]
----
name = regression

features = [
  "classpath:features"
]

tags {
  "include" = ["@regression"]
  exclude = ["@ignore"]
}

env = local
dataset = default
parallel = 1
----

=== Minimal environment config

[source,hocon]
----
baseUrl = "https://example.test"
timeout = 5000
----

Environment config is currently intended to be flat and scalar.
Use values such as URLs, tenant names, timeouts, and simple booleans.
Do not treat nested objects or arrays as part of the supported contract yet.

=== Run

[source,bash]
----
./gradlew regressionRun \
  -Pworkflow=regression \
  -Penv=local \
  -Pdataset=default \
  -Pcommit=abc123
----

The Karate HTML report is written under `build/reports/regression/`.

== Recommended Consumer Layout

[source,text]
----
your-project/
|- build.gradle.kts
`- src/test/resources/
   |- features/
   |  |- user/
   |  `- payment/
   |- workflows/
   |  |- smoke.conf
   |  `- regression.conf
   |- environments/
   |  |- base.conf
   |  |- local.conf
   |  `- staging.conf
   `- datasets/
      |- default/
      `- edge-cases/
----

This layout is conventional, not mandatory. The plugin works with other layouts as long as the
configured directories and classpath feature paths are consistent.

== DSL Reference

=== `regression { }`

Top-level extension:

[source,kotlin]
----
regression {
    workflowsDirs.add("src/test/resources/workflows")
    environmentsDirs.add("src/test/resources/environments")
    datasetsRootDir.set("src/test/resources/datasets")
    datasetProvider.set("local")

    datasets {
        register("default") {
            path.set("default")
        }
    }

    reporting {
        allure {
            enabled.set(true)
        }
        reportPortal {
            enabled.set(false)
        }
    }
}
----

==== `workflowsDirs`

Type: `ListProperty<String>`

Default:

[source,text]
----
["src/test/resources/workflows"]
----

Meaning:

* One or more directories searched in priority order
* Earlier directories override matching keys from later directories
* Missing keys can fall back to later directories

==== `environmentsDirs`

Type: `ListProperty<String>`

Default:

[source,text]
----
["src/test/resources/environments"]
----

Meaning:

* One or more directories searched in priority order
* Resolution is performed for both `base` and the selected environment name

==== `datasetsRootDir`

Type: `Property<String>`

Default:

[source,text]
----
"datasets"
----

Meaning:

* Root directory used by the local dataset provider
* Registered dataset paths are resolved relative to this root

==== `datasetProvider`

Type: `Property<String>`

Default:

[source,text]
----
"local"
----

Current behavior:

* Only `local` is implemented today
* S3 and Git-style providers are roadmap items, not current behavior

==== `datasets { }`

Type: `NamedDomainObjectContainer<DatasetSpec>`

Example:

[source,kotlin]
----
datasets {
    register("default") {
        path.set("default")
    }
    register("incident-2026-04-09") {
        path.set("incidents/2026-04-09")
    }
}
----

Each dataset registration has:

* `name`
  The logical dataset name used from CLI or workflow config
* `path`
  Relative path under `datasetsRootDir`

Default for `path`:

* If omitted, the dataset name itself is used

Fallback behavior:

* If no explicit registration exists, dataset resolution still falls back to
  `datasetsRootDir/<datasetName>`

=== `reporting { }`

Nested reporting extension:

[source,kotlin]
----
reporting {
    allure {
        enabled.set(true)
    }
    reportPortal {
        enabled.set(true)
    }
}
----

==== `allure { }`

[cols="1,1,3"]
|===
|Property |Default |Meaning

|`enabled`
|`false`
|Enables the Allure JUnit5 adapter integration

|`version`
|`2.27.0`
|Version of `io.qameta.allure:allure-junit5`

|`resultsDir`
|`allure-results`
|Directory relative to the Gradle `build/` directory where raw Allure result files are written
|===

When enabled, the plugin:

* Adds `io.qameta.allure:allure-junit5` to `testImplementation`
* Passes `allure.results.directory` to `regressionRun`
* Passes the same property to Gradle `Test` tasks

==== `reportPortal { }`

[cols="1,1,3"]
|===
|Property |Default |Meaning

|`enabled`
|`false`
|Enables the ReportPortal JUnit5 agent integration

|`agentVersion`
|`5.4.1`
|Version of `com.epam.reportportal:agent-java-junit5`

|`endpoint`
|
|ReportPortal server URL

|`apiKey`
|
|ReportPortal authentication token

|`project`
|
|ReportPortal project name

|`launch`
|
|Launch name shown in ReportPortal

|`description`
|
|Optional human-readable launch description

|`attributes`
|
|List of `key:value` or plain tags joined into the format expected by the agent
|===

When enabled, the plugin:

* Adds `com.epam.reportportal:agent-java-junit5` to `testImplementation`
* Passes the `rp.*` system properties to `regressionRun`
* Passes the same `rp.*` properties to Gradle `Test` tasks

Keep `apiKey` out of version control.
Prefer environment variables or Gradle properties.

== Configuration Model

The plugin has its own configuration model, and Karate has its own runtime model.
The plugin resolves workflow, environment, dataset, and reporting inputs before Karate starts.
It then maps the resolved values into Karate through JVM system properties.

=== Public config sources

These are the config sources supported by the public plugin contract today:

[cols="1,1,3"]
|===
|Source |Configured by |Purpose

|Workflow files
|`workflowsDirs`
|Select feature paths, tag filters, default env, default dataset, parallelism, and mode

|Environment files
|`environmentsDirs`
|Provide flat scalar runtime config such as URLs, tenants, timeouts, and flags

|Dataset registry
|`datasetsRootDir` and `datasets { }`
|Resolve a logical dataset name to a local filesystem directory

|Gradle properties
|`-Pworkflow`, `-Penv`, `-Pdataset`, `-Pcommit`, `-Pkarate.user.*`
|Select or override the run inputs; pass user-owned Karate properties

|Reporting DSL
|`reporting { }`
|Configure Allure and ReportPortal integration properties

|Karate runtime/user code
|`karate-config.js`, feature files, environment variables
|Suite-specific config, headers, auth, local servers, and secrets
|===

Internal core code also has generic `ConfigSource` types for classpath resources and system
properties, but the Gradle plugin currently wires workflow and environment config from local
directories only. Treat classpath and system-property config sources as internal extension points,
not public plugin behavior.

=== Plugin config versus Karate config

[cols="1,1,3"]
|===
|Concept |Owner |Notes

|Workflow DSL
|Plugin
|Loaded from `workflowsDirs`; controls what to run

|Environment files
|Plugin
|Loaded from `environmentsDirs`; exposed as `karateGradle.config.<key>`

|Dataset selection
|Plugin
|Resolved to `karateGradle.dataset.path`

|`karate.env`
|Karate, selected by plugin
|The plugin sets the selected env name before Karate starts

|`karate.properties['...']`
|Karate
|Backing compatibility channel for JVM system properties injected by the plugin or user

|`karateGradle`
|Plugin
|Injected into every scenario by the generated runner; direct way to read plugin-resolved context

|`karate-config.js`
|Karate/user
|User-owned bootstrap file for suite behavior such as auth, dynamic headers, and local servers

|Environment variables
|User/runtime
|Recommended source for secrets; read directly from Karate/JVM user code
|===

=== Priority rules

Run input priority:

. `-Pworkflow` selects the workflow file; default is `regression`
. `-Penv` overrides the workflow's `env` field
. `-Pdataset` overrides the workflow's `dataset` field
. `-Pcommit` is optional and is forwarded as `karate.commit`
. `-Pkarate.user.*` and `-Dkarate.user.*` are forwarded unchanged to Karate
. If the same `karate.user.*` key is supplied by both `-P` and `-D`, the `-D` value wins

Workflow and environment directory priority:

. Directories are read in the order configured in `workflowsDirs` and `environmentsDirs`
. Earlier directories have higher priority than later directories
. Missing keys in a higher-priority config can fall back to lower-priority directories
. Within one directory, only the first matching file for a logical name is loaded

File extension priority within one directory:

[source,text]
----
.conf -> .json -> .yaml -> .yml -> .properties
----

Environment merge priority:

. `base` is loaded first as shared defaults
. The selected env, such as `local`, `staging`, or `prod`, overrides `base`
. The merged result is exposed as `karateGradle.config.<key>`
. The same values are also forwarded as `karate.config.<key>` system properties for compatibility

Dataset priority:

. `-Pdataset=<name>` if supplied
. workflow `dataset` field
. `default`
. registered dataset path if one exists
. otherwise `<datasetsRootDir>/<datasetName>`

=== Supported read patterns

These are the supported ways to read configuration during a Karate run:

[cols="1,3"]
|===
|Pattern |Use

|`karateGradle.env`
|Read the environment selected by the plugin

|`karateGradle.workflow.name`
|Read the resolved workflow name

|`karateGradle.dataset.name`
|Read the resolved logical dataset name

|`karateGradle.dataset.path`
|Read the resolved dataset directory

|`karateGradle.config.<key>`
|Read merged flat scalar environment config

|`karateGradle.user.<key>`
|Read explicit user-owned pass-through properties from `-Pkarate.user.<key>` or `-Dkarate.user.<key>`

|`karate.env`
|Read the selected Karate environment name from Karate itself

|`karate.properties['karate.workflow']`
|Compatibility path for the resolved workflow name

|`karate.properties['dataset.path']`
|Compatibility path for the resolved dataset directory

|`karate.properties['karate.commit']`
|Read the optional commit identifier

|`karate.properties['karate.config.<key>']`
|Compatibility path for flat scalar environment config

|`karate.properties['karate.user.<key>']`
|Compatibility path for explicit user-owned pass-through properties

|`java.lang.System.getenv('NAME')`
|Read secrets or process environment values directly
|===

`karateGradle` is injected by the generated runner before scenario steps run. Users do not need
`karate-config.js` just to expose workflow, dataset, or environment config to feature files.

Example feature usage:

[source,gherkin]
----
* url karateGradle.config.baseUrl
* def datasetPath = karateGradle.dataset.path
* def tenant = karateGradle.config.tenant
* def userFlag = karateGradle.user.flag
----

Use `karate-config.js` for user-owned runtime behavior such as auth, headers, local services, or
computed defaults:

[source,javascript]
----
function fn() {
    var config = {
        apiToken: java.lang.System.getenv('API_TOKEN')
    };

    karate.configure('headers', {
        Authorization: 'Bearer ' + config.apiToken
    });

    return config;
}
----

Secrets are intentionally not part of the plugin config contract. Keep them out of workflow and
environment files, and read them from environment variables or a user-managed secret provider at
runtime.

User-owned pass-through properties must use the `karate.user.` prefix. The prefix is kept in
Karate, so `-Dkarate.user.flag=true` is read as
`karate.properties['karate.user.flag']`. Unprefixed `-P` and `-D` properties are not forwarded.
Do not use plugin-owned keys such as `karate.env`, `karate.workflow`, `karate.config.*`, or
`karate.runner.*` for custom values.

== Workflow Definition Reference

Workflows define what runs and with which defaults.

=== Supported file formats

Per directory, lookup order is:

[source,text]
----
.conf -> .json -> .yaml -> .yml -> .properties
----

Within one directory, only the first matching file for the workflow name is loaded.
Across multiple directories, higher-priority directories can override individual keys and
fall back to lower-priority directories for missing keys.

=== Workflow schema

[cols="1,1,3"]
|===
|Field |Default |Meaning

|`name`
|
|Logical workflow name. Required.

|`features`
|`[]`
|Karate feature paths passed into the generated runner

|`tags.include`
|`[]`
|Tags to include

|`tags.exclude`
|`[]`
|Tags to exclude

|`env`
|`base`
|Default environment name if `-Penv` is not supplied

|`dataset`
|`default`
|Default dataset name if `-Pdataset` is not supplied

|`parallel`
|`1`
|Parallelism forwarded into JUnit Platform fixed parallel execution settings

|`mode`
|`standard`
|Reserved workflow mode field currently carried through the model
|===

=== HOCON example

[source,hocon]
----
name = regression

features = [
  "classpath:features/user"
  "classpath:features/payment/payment-lifecycle.feature"
]

tags {
  "include" = ["@regression"]
  exclude = ["@ignore"]
}

env = staging
dataset = edge-cases
parallel = 4
mode = standard
----

=== YAML example

[source,yaml]
----
name: regression
features:
  - classpath:features/user
  - classpath:features/payment/payment-lifecycle.feature
tags:
  include: ["@regression"]
  exclude: ["@ignore"]
env: staging
dataset: edge-cases
parallel: 4
mode: standard
----

=== Notes

* In HOCON, `include` is a reserved word, so quote it inside `tags`
* `features` is optional, but a practical workflow normally specifies one or more paths
* `parallel` affects JUnit Platform configuration, not a separate Karate standalone CLI thread flag

== Environment Resolution Reference

Environment config is resolved by merging:

. `base`
. the selected environment such as `local`, `staging`, or `prod`

The selected environment overrides `base`.

Current contract:

* Keep environment files flat
* Use scalar values only: strings, numbers, booleans
* Treat nested objects and arrays as unsupported for now

=== Supported file formats

Per directory, lookup order is:

[source,text]
----
.conf -> .json -> .yaml -> .yml -> .properties
----

=== Example

[source,hocon]
----
// base.conf
timeout = 5000
connectTimeout = 3000
tenant = "public"
----

[source,hocon]
----
// staging.conf
baseUrl = "https://staging.example.test"
tenant = "staging-a"
----

Effective resolved map:

[source,json]
----
{
  "timeout": 5000,
  "connectTimeout": 3000,
  "tenant": "staging-a",
  "baseUrl": "https://staging.example.test"
}
----

At runtime, the plugin forwards these entries as system properties with the prefix:

[source,text]
----
karate.config.<key>
----

Examples:

* `karate.config.baseUrl`
* `karate.config.timeout`
* `karate.config.tenant`

This forwarding model is the reason the guide recommends flat scalar config only.
Complex nested structures may parse, but they are not guaranteed to behave as real
objects or lists once forwarded into Karate.

== Dataset Resolution Reference

Dataset resolution is logical-name based.

Current provider contract:

* Only the local filesystem provider is implemented
* `datasetProvider.set("local")` is the supported setting today
* S3 and Git-backed providers can be added later but are not available now

Resolution steps:

. Determine the effective dataset name
  Either `-Pdataset=<name>` or the workflow's `dataset` field
. Look up a registered dataset path if one exists
. Otherwise fall back to `<datasetsRootDir>/<datasetName>`
. Verify the resolved directory exists

=== Example

[source,kotlin]
----
regression {
    datasetsRootDir.set("src/test/resources/datasets")

    datasets {
        register("default") {
            path.set("default")
        }
        register("edge-cases") {
            path.set("advanced/edge-cases")
        }
    }
}
----

Result:

* `default` -> `src/test/resources/datasets/default`
* `edge-cases` -> `src/test/resources/datasets/advanced/edge-cases`

If the resolved directory does not exist, the task fails.

== Runtime System Properties

The plugin assembles system properties for the forked JVM.
The most important ones are:

[cols="1,3"]
|===
|Property |Purpose

|`karate.env`
|Selected environment name

|`karate.workflow`
|Workflow name

|`karate.runner.features`

|`karate.runner.tags.include`
|Comma-separated include tags

|Comma-separated exclude tags

* `karate.commit`
* `allure.results.directory`
* `rp.endpoint`
* `rp.api.key`
* `rp.project`
* `rp.launch`
* `rp.description`
* `rp.attributes`

== Logging

`regressionRun` forks a separate JVM for Karate. There are two logging layers:

* Gradle task logs from the plugin
* Karate runtime logs from the forked JVM

=== Gradle task logs

Use normal Gradle flags to control plugin-side task logging:

[source,bash]
----
./gradlew regressionRun --info
./gradlew regressionRun --debug
----

This affects messages emitted by the Gradle task, such as workflow selection and task execution
details. It does not change Karate's internal logger level.

=== Karate runtime logs

Control Karate and library log levels with a standard logging config on the test runtime classpath.
For Logback, place `logback-test.xml` under `src/test/resources`:

[source,xml]
----
<configuration>
    <!-- Use <configuration debug="true"> temporarily to see which Logback file was loaded. -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <logger name="com.intuit.karate" level="INFO"/>
    <logger name="org.openprojectx.karate" level="INFO"/>

    <root level="WARN">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
----

Set `com.intuit.karate` to `DEBUG` only when you need detailed Karate internals. Keeping the
root logger at `WARN` avoids noisy dependency logs during normal regression runs.

If no `logback-test.xml` or `logback.xml` is found, Logback falls back to its default console
configuration. That fallback is verbose because the default root logger level is `DEBUG`, so
examples and real projects should provide their own `logback-test.xml`.

To inspect which Logback config is actually used, temporarily change the opening tag to:

[source,xml]
----
<configuration debug="true">
----

Logback will print internal status messages during startup, including the discovered config
resource and its classpath location. Revert this after troubleshooting to avoid noisy CI logs.

=== Request and response detail

Karate request and response printing is controlled in `karate-config.js`, not by the plugin:

[source,javascript]
----
function fn() {
    karate.configure('logPrettyRequest', true);
    karate.configure('logPrettyResponse', true);
    return {};
}
----

Enable these only when needed. Request and response logs can include headers, payloads, or tokens
if the feature files send them.

=== Pass-through properties and logging

The `karate.user.*` pass-through is intended for user test configuration:

[source,bash]
----
./gradlew regressionRun -Dkarate.user.flag=true
----

It is not the preferred way to configure logging frameworks. Use `logback-test.xml` or the
logging framework's own supported configuration mechanism for log levels.

== Reporting Guide

=== Allure

Configuration:

[source,kotlin]
----
plugins {
    id("org.openprojectx.karate.gradle")
    id("io.qameta.allure") version "3.0.1"
}

allure {
    adapter { autoconfigure.set(false) }
}

regression {
    reporting {
        allure {
            enabled.set(true)
            resultsDir.set("allure-results")
        }
    }
}
----

Run and generate the HTML report:

[source,bash]
----
./gradlew regressionRun
./gradlew test
./gradlew allureReport
----

Output locations:

* Raw results: `build/allure-results/`
* HTML report: `build/reports/allure-report/`

=== ReportPortal

Configuration:

[source,kotlin]
----
regression {
    reporting {
        reportPortal {
            enabled.set(true)
            endpoint.set(providers.environmentVariable("RP_ENDPOINT"))
            apiKey.set(providers.environmentVariable("RP_API_KEY"))
            project.set("karate-regression")
            launch.set("nightly-regression")
            description.set("Nightly workflow-driven run")
            attributes.set(listOf("team:qa", "env:staging"))
        }
    }
}
----

Run:

[source,bash]
----
./gradlew regressionRun -Pworkflow=regression
----

or:

[source,bash]
----
./gradlew test
----

ReportPortal has no local HTML output mode.
It streams results to the configured server.

=== Reporter behavior summary

[cols="1,3"]
|===
|Execution path |Behavior

|`regressionRun`
|Runs through generated JUnit Platform launcher, so JUnit listeners can attach

|`test`
|Runs through Gradle's standard JUnit execution path, so JUnit listeners can attach

|`allureReport`
|Post-processes Allure raw results into static HTML
|===

== Example Consumer Configuration

[source,kotlin]
----
plugins {
    id("org.openprojectx.karate.gradle")
    id("io.qameta.allure") version "3.0.1"
}

allure {
    adapter { autoconfigure.set(false) }
}

regression {
    workflowsDirs.add("src/test/resources/workflows")
    environmentsDirs.add("src/test/resources/environments")
    datasetsRootDir.set("src/test/resources/datasets")

    datasets {
        register("default") {
            path.set("default")
        }
        register("edge-cases") {
            path.set("advanced/edge-cases")
        }
    }

    reporting {
        allure {
            enabled.set(true)
        }
        reportPortal {
            enabled.set(false)
        }
    }
}
----

== Example `karate-config.js`

[source,javascript]
----
function fn() {
    var env = karate.env || 'local';
    var config = {
        env: env,
        workflow: karate.properties['karate.workflow'],
        datasetPath: karate.properties['dataset.path'],
        baseUrl: karate.properties['karate.config.baseUrl'],
        tenant: karate.properties['karate.config.tenant'] || 'public'
    };

    karate.configure('headers', {
        Accept: 'application/json',
        'Content-Type': 'application/json',
        'X-Tenant': config.tenant
    });

    return config;
}
----

== CI Usage

The plugin is designed so CI only needs to pass parameters.

=== Jenkins example

[source,groovy]
----
sh """
./gradlew regressionRun \
  -Pworkflow=${params.WORKFLOW} \
  -Penv=${params.ENV} \
  -Pdataset=${params.DATASET} \
  -Pcommit=${params.GIT_COMMIT}
"""
----

=== GitHub Actions example

[source,yaml]
----
- name: Run workflow-driven Karate regression
  run: |
    ./gradlew regressionRun \
      -Pworkflow=regression \
      -Penv=staging \
      -Pdataset=default \
      -Pcommit=${GITHUB_SHA}
----

== Troubleshooting

=== `Workflow '<name>' not found`

Check:

* The file exists under one of the configured `workflowsDirs`
* The file name matches the logical workflow name
* A higher-priority directory does not contain an unexpected conflicting file

=== Dataset resolution failure

Typical cause:

* The resolved dataset directory does not exist

Check:

* `datasetsRootDir`
* explicit dataset registration paths
* the value passed via `-Pdataset`

=== Environment values not visible in Karate

Check:

* `base.conf` and `<env>.conf` are in one of the configured environment directories
* your `karate-config.js` reads `karate.properties['karate.config.<key>']`
* the selected environment is the one you expect

=== Reporting integration does not fire

Check:

* The reporter is enabled in `reporting { }`
* The necessary plugin or downstream tool is present where required
* Credentials such as `RP_API_KEY` are available
* You are looking at the correct output:
  Allure uses `build/allure-results/` plus `allureReport`, while ReportPortal streams remotely

=== Long-running process after tests complete

Typical cause:

* A test-support server or helper thread was started inside the forked JVM and not stopped

Recommendation:

* Make embedded servers and external resources shut down explicitly at suite end
* Do not rely solely on JVM shutdown hooks if those resources keep non-daemon threads alive

== Migration Notes

=== From older standalone-runner assumptions

If you previously assumed `regressionRun` behaved like a Karate standalone CLI invocation,
update that assumption.

Current behavior:

* `regressionRun` is JUnit-based
* listener-driven tooling can participate
* generated JUnit entry points are part of the plugin's normal execution model

This is intentional and aligns the plugin with the wider Java tooling ecosystem.

== Summary

`karate-gradle` gives you:

* workflow-aware execution through `regressionRun`
* JUnit Platform compatibility for integrations
* simple environment and dataset resolution
* opt-in reporting integrations
* a Gradle-native model suitable for both local development and CI

For practical examples, see the consumer build under `example/`.
